# 忆往昔 · 内容共创流程指南（SOP）

> 版本：v1.0（2026-08-16）
> 目标：把「内容共建」从"能跑"细化到"可运营"——明确角色、认领、审核、署名、激励全流程。
> 适用：内容共创仓库（拟拆出为独立 GitHub 仓库，本文档将随仓发布）。
> 关联：`content/README.md`（内容规范）、`content/CONTRIBUTING.md`（入门指南）、`content/OWNERS.md`（治理）、`content/LICENSE`（协议）、`docs/content-plan.md`（内容建设批次）。

---

## 1. 共创总览：一个贡献的完整生命周期

```
发现缺口 → 认领 → 撰写/录入 → 自检 → PR → CI 门禁 → 人类审核 → 合并 → 状态提升 → 署名与致谢
   │        │        │          │      │       │        │         │        │           │
 选题池   issue   content/   check.py  PR   0 错误   OWNERS     main    状态机     AUTHORS/
 4 路源   认领    写 md      本地跑    提交   自动     审阅      分支     升级      贡献者榜
```

每个环节的负责人、工具、验收标准见下文。

## 2. 角色与权限（RACI）

| 角色 | 谁能担任 | 权限 | 典型工作 |
|------|----------|------|----------|
| **Contributor 贡献者** | 任何人 | 提 issue / 提 PR | 录入原文、补译文注释、校勘、修人物条目 |
| **Reviewer 审阅者** | 维护者指定的资深贡献者 | 审 PR、批注 | 逐条核对引用、检查客观性、把关质量 |
| **Maintainer 内容维护者** | owner 任命 | 合并 PR、状态审批、异文裁决 | 定版、提升 PUBLISHED、处理争议 |
| **Maintainer 技术维护者** | owner 任命 | schema / check.py / sync.py / CI | 工具链维护、门禁升级 |
| **Owner 仓库负责人** | 创始人 | 最终裁决、开源发布、LICENSE 变更 | 拍板、任命、对外 |

> 决策模型：**贡献者提、审阅者评、维护者定、owner 终裁**。普通贡献者不能自行把内容置为 PUBLISHED（状态机强制）。

## 3. 选题与认领（找活干）

### 3.1 选题从哪来

| 来源 | 说明 | 入口 |
|------|------|------|
| 经典全文缺口 | 25 部经典中尚无章节全文的（见 `docs/content-plan.md` 批次表） | 对应 `classics/{slug}/` 目录空 |
| 知识卡片关联需求 | 卡片引用经典但章节缺失 | 卡片 sources 悬空 |
| 内容批次计划 | 按 P0→P1→P2 排期 | `docs/content-plan.md` |
| 社区提议 | 新经典/新人物/新概念 | issue 讨论 |

### 3.2 认领规则

1. **先查再认**：确认 `classics/{slug}/chapters/` 是否已有人认领/完成（看 `classic.md` 的 `claimed_by` 字段 + issue 列表）。
2. **开 issue 认领**：标题「认领：录入《庄子·齐物论》」，注明范围（篇/章/人物）、预期完成时间、公版来源。
3. **登记**：维护者在 `classics/{slug}/classic.md` 写入 `claimed_by: <authors-id>`。
4. **超时回收**：认领 30 天无进展 → 维护者在 issue 回收，释放给他人。
5. **冲突解决**：撞车时先来后到 + 协商拆分；无法协商由内容维护者裁定。

### 3.3 认领状态机（issue 标签）

| 标签 | 含义 |
|------|------|
| `认领:available` | 待认领 |
| `认领:in-progress` | 已被认领，进行中 |
| `认领:done` | 已提交 PR 待审 |
| `认领:stale` | 超时待回收 |

## 4. 撰写规范（写什么、怎么写）

### 4.1 内容类型与最低要求

| 类型 | 文件位置 | 必填字段 | 正文要求 |
|------|----------|----------|----------|
| 经典元数据 | `classics/{slug}/classic.md` | slug/title/text_source/review_status | 背景/结构/核心思想 |
| 章节原文 | `classics/{slug}/chapters/{NNN}.md` | classic/chapter_number/text_source/contributors | `## 原文` 必填；`## 今译`/`## 注释` 推荐 |
| 概念词条 | `entities/concepts/{slug}.md` | slug/name/summary | 基础定义，深度诠释归卡片 |
| 人物条目 | `entities/persons/{slug}.md` | slug/name/summary | 只写事实，不做评价 |
| 诗词 | `poetry/**` | 见 poetry.schema.json | 原文 + 出处 |

### 4.2 可信度分级（写前先定）

| 级 | 含义 | 能否 PUBLISHED |
|----|------|---------------|
| S | 学界共识/公版定本 | ✅ |
| A | 主流观点 | ✅ |
| B | 一般说法（含 AI 生成待校勘） | ✅（可） |
| C | 存疑/少数派 | ❌（状态机硬约束） |

### 4.3 AI 使用规则

- **允许**：AI 辅助录入初稿、比对版本、起草译文。
- **禁止**：AI 作为 contributor 署名；AI 生成内容不标 `ai_used`。
- **强制**：有 `ai_used` 且 contributors 为空 → 状态机禁止离开 DRAFT（check.py 强制）。
- AI 初稿必须有人类认领审核后才能升级（reviewers 留痕）。

## 5. 提交流程（PR 全流程）

### 5.1 本地自检（提交前必做）

```bash
cd content
python tools/check.py          # 必须 0 错误（警告可接受但建议清零）
```

### 5.2 PR 清单

| 检查项 | 标准 |
|--------|------|
| 范围 | 一个 PR 一个主题（一章原文/一位人物/一个概念） |
| 署名 | contributors/reviewers 用 AUTHORS.yaml 已注册 ID |
| 溯源 | text_source 标注公版来源 + 版本 + 校点者 |
| AI 标注 | 用了 AI 必须标 ai_used |
| 状态 | 新内容 DRAFT 起步，不直接 PUBLISHED |
| 描述 | 说明改动 + 版本来源 + 认领 issue 号 |

### 5.3 CI 门禁（自动）

PR 触发 `.github/workflows/ci.yml`：
- `content-check` job：跑 `python3 content/tools/check.py`，**0 错误**才放行。
- 失败 → PR 标红，贡献者修复后重新提交。

### 5.4 人工审核矩阵

| 内容类型 | 审阅重点 | 审阅者 |
|----------|----------|--------|
| 古籍原文 | 版本来源、异文处理、编号对齐 | 内容维护者 |
| 译文/注释 | 准确性、不神化不贬低、平衡性 | 内容维护者 + 领域审阅者 |
| 人物条目 | 客观中性、事实无硬伤 | 内容维护者 |
| 概念词条 | 定义客观、无过度诠释 | 内容维护者 |
| 工具/schema | 向后兼容、check.py 通过 | 技术维护者 |

### 5.5 合并与状态提升

1. PR 合并后：内容仍是 DRAFT。
2. 维护者审核通过 → 状态提升 `DRAFT → APPROVED`。
3. 发布上线 → `APPROVED → PUBLISHED`（sync.py 增量入库）。
4. 勘误：PUBLISHED 文件不直接改，走新版本（README §6.3）。

## 6. 审核与裁决（有争议怎么办）

### 6.1 审核层级

```
自动(CI/check.py) → 人类审阅(Reviewer) → 维护者审批(Maintainer) → 争议终裁(Owner)
```

### 6.2 需要维护者裁决的事项

1. 异文取舍（不同版本原文冲突）
2. 状态提升的最终确认
3. 内容客观性/人物表述争议
4. 新内容类型批准
5. LICENSE 变更、版权风险下线

### 6.3 裁决流程（留痕）

1. PR/issue 公开辩论，摆版本、摆出处。
2. 内容维护者裁定 → 记录「裁决人 + 日期 + 依据」。
3. 不服 → 升级 owner 终裁（同样留痕）。

## 7. 署名与致谢（干完活得到什么）

### 7.1 署名机制

| 动作 | 记录位置 | 说明 |
|------|----------|------|
| 实质性录入/校勘/注释/翻译 | 文件 `contributors` | 角色：transcribe/annotate/translate/collate |
| 审核确认 | 文件 `reviewers` | 审核链留痕 |
| 新贡献者注册 | `AUTHORS.yaml` | 一人一 ID，全仓复用 |
| 纯 typo/格式 | git 提交记录 | 不署名（靠 git blame） |

### 7.2 激励（建议，待 owner 拍板）

| 激励 | 机制 |
|------|------|
| 贡献者榜 | 前端 `/contributors` 页展示（已上线） |
| 里程碑徽章 | 累计 N 章录入/ N 次审核 → 徽章 |
| 审阅者晋升 | 长期高质量审阅 → 维护者提名 |
| 致谢 | 版本发布时鸣谢名单 |

## 8. 开源协议与合规（发布底线）

| 内容 | 协议 |
|------|------|
| 古籍/诗词原文 | 公有领域（公版校点本，text_source 标注） |
| 人物条目（事实汇编） | CC BY 4.0 |
| 译文/注释/评点 | CC BY-SA 4.0 |
| 工具/schema | MIT |

**红线**：
- 不转录有版权的现代整理本（只收公版）。
- 医书/养生内容带 `disclaimer` 免责声明。
- 人物表述客观中性，不构成评价。

## 9. 里程碑（共创仓库发展路线）

| 阶段 | 目标 | 验收 |
|------|------|------|
| M1 基础设施（当前） | content/ 拆独立仓库 + CI + LICENSE + 贡献者页 | 仓库可公开，新贡献者可提 PR |
| M2 冷启动 | 核心 5-8 部经典全文 + 首批种子贡献者 | 有真实 PR 合并记录 |
| M3 认领运转 | 认领制 + 审阅制上线，周更 | 每周有 PR 进出 |
| M4 社区化 | 贡献者榜、里程碑徽章、领域审阅组 | 月活贡献者 > 5 人 |
